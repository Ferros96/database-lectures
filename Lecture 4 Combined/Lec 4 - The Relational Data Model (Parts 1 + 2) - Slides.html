01 · From tables to relations

The relational model in one idea

DEFINITION

The relational model represents the database as a collection of relations. Each relation looks like a table of values.

In plain words

A relation is basically a table. A relational database is just a set of tables, like the five tables of the University database.

Example: the University database is 5 relations
STUDENTone row per student
COURSEone row per course
SECTIONone row per course section
GRADE_REPORTone row per grade a student received
PREREQUISITEone row per course–prerequisite pair
⏱ 2 min
Goal

Students leave this slide thinking ‘relation = table’.

Say

Read the definition, then say it again in your own words: a relational database is a set of tables, and each table is called a relation.

How to explain it

Use the University database from Lecture 3 as the anchor. Point at the five names in the example box and say ‘this database is five relations’. Do not mention keys or constraints yet; that is Part 2.

Example to use

Ask a student to name what one row of GRADE_REPORT means (one grade a student received). That shows every relation stores one kind of thing.

Watch out for

Some students confuse ‘relation’ with ‘relationship’ from ER diagrams. Say clearly: in this model a relation is a table, not a link between tables.

01 · From tables to relations

Relation schema: the heading of the table

DEFINITION

A relation schema R(A1, A2, …, An) is made up of a relation name R and a list of attributes A1, A2, …, An.

In plain words

The schema describes the table: its name and its column names. It does not contain any data. Think of it as the empty table heading.

Example: the STUDENT schema
STUDENT (Name, SSN, HomePhone, Address, Office_Phone, Age, GPA)
R = STUDENTA1 = NameA2 = SSN… A7 = GPA
⏱ 3 min
Goal

Separate the description of a table from its data.

Say

A relation schema is the name plus the list of attributes. It has no data in it. Think of it as the empty table heading.

How to explain it

Write R(A1, A2, …, An) on the board. Underneath, write STUDENT(Name, SSN, …) and draw lines: R becomes STUDENT, A1 becomes Name, and so on. The mapping chips on the slide show the same thing.

Example to use

Compare to a blank form: the form with its field labels is the schema; each filled-in copy is a tuple.

Watch out for

Students write the schema with values in it. Stress: only names go in a schema, never data.

01 · From tables to relations

Domain: the allowed values of a column

DEFINITION

A domain D is a set of atomic values. A data type or format is also specified for each domain.

In plain words

A domain is the list of values a column may hold. Atomic means each value is one single, indivisible value, never a list.

Examples from the lecture
Phone_numbers7-digit numbers valid in an area code; format ddd-dddd (d = decimal digit)
Grade_point_averagesreal numbers between 0 and 4
Employee_agesvalues between 15 and 80
Social_security_numbersthe valid 9-digit SSNs
⏱ 3 min
Goal

Understand a domain as allowed values plus a format.

Say

A domain is the set of values a column may hold. Each value is atomic, which means one single value, never a list.

How to explain it

Explain the two halves of a domain: the meaning (what values make sense) and the data type or format. Use Phone_numbers: the meaning is ‘valid phone numbers in this area code’, the format is ddd-dddd.

Example to use

Ask: could an age of 200 be in Employee_ages? No, the domain is 15 to 80. Could a GPA be 3.5? Yes.

Watch out for

Students think a domain is just the data type (‘integer’). Point out that Employee_ages and a list of shoe sizes might both be integers but are different domains.

Relation state: the data at one moment

DEFINITION

A relation state r of the relation schema R(A1, A2, …, An), denoted r(R), is a set of n-tuples r = {t1, t2, …, tm}.

In plain words

The state is the rows stored in the table right now. Each tuple holds n values, one for each attribute. The state changes whenever data is added, changed or removed.

Example: part of r(STUDENT)

⏱ 3 min
Goal

Schema vs state.

Say

The relation state r(R) is the set of tuples stored in the table right now. Each tuple has n values, one per attribute.

How to explain it

Link back to Lecture 3: schema versus state, or intension versus extension. The schema rarely changes; the state changes every time someone inserts, deletes or updates a row. Point at t1, t2, t3 in the note under the table.

Example to use

Today’s state has 5 students. Next semester new students are inserted: new state, same schema.

Watch out for

Notation trips people up: capital R is the schema, small r is the state. Write both side by side on the board.

02 · Characteristics of relations

Atomic values only

DEFINITION

Each value in a tuple is an atomic value. Composite and multi-valued attributes are not allowed.

In plain words

One cell holds one value. You cannot store a list or a value with inner parts in a single cell.

How the relational model handles them
✗ Not allowed in a cell
  • Composite attributes
  • Multi-valued attributes
✓ Represented instead by
  • Only their simple component attributes
  • A separate relation
⏱ 3 min
Goal

One cell, one value.

Say

Each value in a tuple must be atomic. Composite and multi-valued attributes from the ER model are not allowed inside a cell.

How to explain it

Work through both columns of the example. Composite: an address with street, city and zip is stored as its simple parts. Multi-valued: a student with several phone numbers needs a separate relation.

Example to use

Draw a quick PHONES(SSN, Phone) table on the board with two rows for the same student. That is the ‘separate relation’.

Watch out for

Students may suggest Phone1, Phone2, Phone3 columns. Explain why that fails: what if someone has four, and most people would have NULLs.

Four kinds of constraints

In a relational database, there are generally many restrictions or constraints on the actual values in a database state.

Domain constraints

01

Every value comes from its attribute’s set of allowed values.

Key constraints

02

No two tuples are the same; a key identifies each tuple.

Entity integrity

03

A primary key value can never be NULL.

Referential integrity

04

A reference must point to a tuple that exists.

Domain constraints

DEFINITION

Within each tuple, the value of each attribute A must be an atomic value from the domain dom(A).

In plain words

Every cell must hold one value of the right kind: an age must be a number in the age domain, a date must be a date, and so on.

Data types typically associated with domains
Numericintegers and real numbers
Charactersfixed-length and variable-length strings
Date / Timedates and times
Moneymonetary amounts
⏱ 2 min
Goal

Domain constraint = type and range.

Say

Every value in a tuple must be an atomic value from that attribute’s domain, dom(A).

How to explain it

Connect directly to Part 1: there we defined a domain; here the rule says the data must obey it. Run through the data types in the example box.

Example to use

Inserting Age = 'twenty' or GPA = 5.7 breaks the domain constraint.

04 · Keys

Key constraints

A relation is a set of tuples

A relation is defined as a set of tuples.

Tuples must be distinct

No two tuples can have the same combination of values for all their attributes.

Keys identify tuples

The value of a key attribute can be used to identify uniquely each tuple in the relation.

Time-invariant

A key is determined from the meaning of the attributes; the property must continue to hold when we insert new tuples.

⏱ 3 min
Goal

Understand uniqueness and time-invariance.

Say

Because a relation is a set, no two tuples can be identical. A key is an attribute, or set of attributes, whose value is enough to identify a tuple.

How to explain it

Spend most of the time on the last point: a key must hold for any data we might insert in the future, not just today. We decide keys from the meaning of the attribute, not by looking at the current rows.

Example to use

Today no two students may share a birthday in our small table, but birth date is obviously not a key.

NULL values constraint

DEFINITION

A constraint on attributes specifies whether null values are or are not permitted. If NULLs are not permitted, the attribute is NOT NULL.

In plain words

For some columns we can say: this value must always be filled in. That rule is called NOT NULL.

Example
STUDENT.Name  NOT NULL

If every STUDENT tuple must have a valid, non-null value for Name, then Name of STUDENT is constrained to be NOT NULL.

⏱ 2 min

NOT NULL as a constraint.

Say

We can declare that an attribute must always have a value. That is the NOT NULL constraint.

Contrast with Part 1: Office_phone was allowed to be NULL, but Name should not be, because every student has a name.

05 · Relational database schema

Relational database schema and state

DEFINITION

A relational database schema S = {R1, R2, …, Rm} is a set of relation schemas plus a set of integrity constraints IC. A database state DB = {r1, r2, …, rm} is a set of relation states, where each ri is a state of Ri.

In plain words

The database schema is all the table headings plus all the rules. A database state is all the tables’ data at one moment, and it is only valid if it satisfies every rule in IC.

Example
Company = {EMPLOYEE, DEPARTMENT, DEPT_LOCATIONS, PROJECT, WORKS_ON, DEPENDENT}

Referential integrity constraint

DEFINITION

Specified between two relations to keep their tuples consistent: a tuple in one relation that refers to another relation must refer to an existing tuple in that relation.

In plain words

If a row points to another table, the thing it points to must really exist. An employee cannot work for a department that isn’t there.

A reference must point to something that exists.

Say

Referential integrity is a rule between two relations: if a tuple refers to another relation, it must refer to a tuple that really exists there.

Foreign key (FK): the two rules

DEFINITION
FK of R1 → R2

Referential integrity is based on the concept of a foreign key. A set of attributes FK in relation schema R1 is a foreign key of R1 that references R2 if it satisfies two rules.

The two rules

1. Same domain The attributes in FK have the same domain(s) as the primary key attributes PK of R2; FK is said to reference (refer to) R2.
2. Exists or is NULL A value of FK in a tuple t1 of r1(R1) either occurs as a value of PK for some tuple t2 in r2(R2), or is null.
Referential integrity constraints typically arise from the relationships among the entities represented by the relation schemas.
⏱ 3 min
Goal

The formal foreign key definition.

Say

Referential integrity is built on foreign keys. A foreign key must have the same domain as the primary key it references, and every value must either exist as a primary key value there or be NULL.

How to explain it

Apply both rules to EMPLOYEE.Dno out loud: rule 1, Dno and Dnumber are both department numbers; rule 2, each Dno is 5, 4 or 1, or NULL.

Watch out for

Highlight the difference with entity integrity: a primary key may never be NULL, but a foreign key may be NULL (for example, an employee not yet assigned to a department).

Key takeaways

  1. 01

    A relational database is a collection of relations: tuple = row, attribute = column header, relation = table, domain = allowed atomic values.

  2. 02

    A relation schema R(A1, …, An) has degree n; a relation state r(R) is a set of n-tuples, in no particular order.

    Values are atomic and may be NULL when unknown.

  4. 04

    Domain and key constraints: every value comes from dom(A); one candidate key is chosen as the (underlined) primary key.

    Entity integrity: no primary key value can be NULL. Referential integrity: a foreign key matches an existing primary key value, or is NULL.
