    01

    Characteristics of the database approach

    What makes it different from writing programs over files

    File processing vs the database approach

    Several characteristics distinguish the database approach from the much older approach of writing customized programs to access data stored in files.

    Traditional file processing

    • Each user defines and implements the files needed for a specific application as part of programming that application.
    • Example: files of students’ data may be implemented as part of many applications, which causes data redundancy.
    vs

    Database approach

    • A single repository maintains data that is defined once.
    • It is then accessed by various users repeatedly through queries, transactions and application programs.

    1. Self-describing nature of a database system

    Database system

    • Contains not only the database itself but also a complete definition or description of the database structure and constraints (meta-data).
    vs

    Traditional file processing

    • Data definition is part of the application programs themselves.

    2. Insulation between programs and data

    Traditional file processing

    • The structure of data files is embedded in the application programs.
    • Any change to the structure of a file may require changing all programs that access that file.
    vs

    Databases

    • The structure of data files is stored in the DBMS catalog, separately from the access programs.
    This separation is also called data abstraction.

    3. Support of multiple views of the data

    A database typically has many types of users, each of whom may need a different perspective or view. A view may be a subset of the database, or it may contain virtual data derived from the database files but not explicitly stored.

    User 1: transcripts

    Interested only in accessing and printing the transcript of each student.

    User 2: prerequisites

    Interested only in checking that students have taken all the prerequisites of each course they register for.

    4. Sharing of data and multiuser transaction processing

    DEFINITION
    Multiuser DBMS

    Must allow multiple users to access the database at the same time.

    How it stays correct

    Concurrency control Software that ensures several users updating the same data do so in a controlled manner, so the result of the updates is correct.
    Example: airline seats When several reservation agents try to assign a seat on a flight, the DBMS ensures each seat can be accessed by only one agent at a time.

    1. Controlling redundancy: the problem

    In file processing, every user group maintains its own files. Storing the same data multiple times leads to three problems:

    Duplication of effort

    A single logical update, such as entering data on a new student, must be performed multiple times: once for each file where student data is recorded.

    Wasted storage

    Storage space is wasted when the same data is stored repeatedly; this may be serious for large databases.

    Inconsistency

    Files that represent the same data may become inconsistent when an update is applied to some files but not to others.

    1. Controlling redundancy: the database solution

    Integrated views

    The views of different user groups are integrated during database design.

    One place to store data

    Each item is stored only once.

    Data normalization

    Ensures consistency and saves storage space.

    2. Restricting unauthorized access

    Not everyone sees everything

    When many users share a large database, most users are likely not authorized to access all of its information.

    Different permissions

    Some users may only retrieve data, while others may retrieve and update it.

    Accounts and passwords

    Users are given account numbers protected by passwords, which they use to gain access to the database.

    3. Providing backup and recovery

    Recovery facilities

    A DBMS must provide facilities for recovering from hardware or software failures.

    Backup & recovery subsystem

    This part of the DBMS is responsible for recovery.

    Disk backup

    Also necessary in case of a catastrophic disk failure.

    4. Providing multiple user interfaces

    Users with varying levels of technical knowledge use a database, so a DBMS should provide a variety of user interfaces.

    Apps

    For mobile users.

    Query languages

    For users who query the data.

    Programming language interfaces

    For application programmers.

    5. Enforcing integrity constraints

    DEFINITION
    Integrity constraints

    A DBMS should provide capabilities for defining and enforcing them. The simplest type specifies a data type for each data item.

    Examples from the STUDENT record

    Class Must be a one-digit integer.
    Name Must be a string of no more than 30 alphabetic characters.
    03

    People and limits

    Who uses a database, and when a DBMS is not worth it

    Database users

    Database administrators

    Authorize access to the database, coordinate and monitor its use, and acquire software and hardware resources as needed.

    Database designers

    Identify the data to be stored in the database and choose appropriate structures to represent and store it.

    End users

    People whose jobs require access to the database for querying, updating and generating reports.

    When not to use a DBMS

    Overhead costs of a DBMS

    • High initial investment in hardware, software and training
    • The generality a DBMS provides for defining and processing data
    • Overhead for security, concurrency control, recovery and integrity functions
    vs

    Build a custom application instead when…

    • The application is simple, well-defined and not expected to change
    • There are stringent real-time requirements DBMS overhead may not meet
    • It is an embedded system with limited storage where a general-purpose DBMS would not fit
    • There is no multiple-user access to data

    Key takeaways

    1. 01

      The database approach stores data once, in a single repository, instead of in files owned by each application.

    2. 02

      Four characteristics: self-describing, program–data insulation, multiple views, multiuser sharing.

    3. 03

      Five advantages: controlled redundancy, restricted access, backup & recovery, multiple interfaces, integrity constraints.

    4. 04

      A DBMS has overhead; simple, real-time, embedded or single-user applications may not need one.

    Q1Why does traditional file processing cause data redundancy?

    Each user defines and implements their own files as part of each application, so the same data (e.g. students’ data) is stored in many applications’ files.

    Q2What does “self-describing” mean for a database system?

    The system contains not only the database but also a complete description of its structure and constraints (meta-data) in the catalog.

    Q3What is a view?

    A perspective on the database for a user type: a subset of the database, or virtual data derived from the database files but not explicitly stored.

    Q4Which DBMS software keeps simultaneous updates correct?

    Concurrency control software.

    Q5Name the three problems caused by redundancy.

    Duplication of effort, wasted storage space, and inconsistent data.

    Q6Give two situations where a DBMS may not be desirable.

    Any two of: simple, well-defined applications not expected to change; stringent real-time requirements; embedded systems with limited storage; no multiple-user access.
