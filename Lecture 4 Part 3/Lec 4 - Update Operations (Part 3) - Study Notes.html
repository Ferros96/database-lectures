    01

    Update operations

    The three operations that change a database state

    Update operations

    From the lecture · Lecture 4 · Part 3
    • The operations of the relational model can be categorized into retrievals and updates.
    • There are three basic operations that can change the states of relations (tables) in the database:
      • Insert to insert new data.
      • Delete to delete old data.
      • Update (or Modify) to modify existing data records.
    • Whenever these operations are applied, the integrity constraints specified on the relational database schema should not be violated.
    In plain words

    Retrievals only read data. Insert, delete and update change it, and every change is checked: after the operation, the database state must still satisfy all the constraints from Part 2 (domain (allowed values), key, entity integrity, referential integrity).

    Hiring an employee = insert · an employee leaves = delete · a pay rise = update.

    What can each operation violate?

    OperationDomainKeyEntity integrityReferential integrity
    INSERT✓can violate✓can violate✓can violate✓can violate
    DELETE———✓can violate
    UPDATE✓if a value is outside its domain✓if a key value changes✓if a primary key becomes NULL✓if a foreign key or a referenced key changes
    Insert: all four. Delete: only referential integrity. Update: depends on which attribute (column) is changed.
    02

    The Insert operation

    Adding a new tuple

    The Insert operation

    From the lecture · Lecture 4 · Part 3
    • The insert operation provides a list of attribute (column) values for a new tuple (row) t that is to be inserted into a relation (table).
      • Domain constraints can be violated if an attribute value is given that does not appear in the corresponding domain (allowed values) or is not of the appropriate data type.
      • Key constraints can be violated if a key value in the new tuple t already exists in another tuple in the relation.
      • Entity integrity can be violated if any part of the primary key of the new tuple t is NULL.
      • Referential integrity can be violated if the value of any foreign key in t refers to a tuple that does not exist in the referenced relation.
    In plain words

    Insert can violate all four constraints. For each new tuple the DBMS asks four questions: Is every value in its domain? Is the key value new? Is the primary key filled in (no NULL)? Does every foreign key point to an existing tuple?

    Insert example 1

    INSERT⟨'Cecilia', 'F', 'Kolonsky', NULL, '1960-04-05', '6357 Windy Lane, Katy, TX', F, 28000, NULL, 4⟩into EMPLOYEE
    EMPLOYEE

    Only Fname, Lname, Ssn, Super_ssn and Dno are shown. Ssn is the primary key.

    ✗ REJECTED · ENTITY INTEGRITY

    “This insertion violates the entity integrity constraint (NULL for the primary key Ssn), so it is rejected.”

    Why: The new tuple (row) has NULL for the primary key Ssn, so the insertion violates entity integrity and is rejected.

    INSERT⟨'Alicia', 'J', 'Zelaya', '999887777', '1960-04-05', '6357 Windy Lane, Katy, TX', F, 28000, '987654321', 4⟩into EMPLOYEE

    ✗ REJECTED · KEY CONSTRAINT

    “This insertion violates the key constraint because another tuple (row) with the same Ssn value already exists in the EMPLOYEE relation (table), and so it is rejected.”

    Why: Another tuple with the same Ssn value (999887777) already exists in EMPLOYEE, so the insertion violates the key constraint and is rejected.

    Why: Dno is a foreign key to DEPARTMENT, and no DEPARTMENT tuple has Dnumber = 7. The insertion violates referential integrity.

    03

    The Delete operation

    Removing tuples

    The Delete operation

    From the lecture · Lecture 4 · Part 3
    • The Delete operation can violate only referential integrity.
    • This occurs if the tuple (row) being deleted is referenced by foreign keys from other tuples in the database.
    • To specify deletion, a condition on the attributes (columns) of the relation (table) selects the tuple (or tuples) to be deleted.
    In plain words

    Deleting adds no values, so it cannot create a bad value, a duplicate key or a NULL key. The only thing it can break is a reference: if other tuples point at the deleted tuple, they are left pointing at nothing.

    Check a delete by asking: who points at this tuple? Follow every foreign key arrow that ends at this relation.

    Delete example 1

    DELETEthe WORKS_ON tuple with Essn = '999887777' and Pno = 10from WORKS_ON
    WORKS_ON
    PRIMARY KEYEssnPRIMARY KEYPnoHours
    3334455552010.0
    9998877773030.0
    9998877771010.0
    9879879871035.0
    987987987305.0

    Part of the WORKS_ON state. (Essn, Pno) is the primary key.

    ✓ ACCEPTED

    “This deletion is acceptable and deletes exactly one tuple (row).”

    Why: No foreign key refers to WORKS_ON tuples, so removing one cannot break a reference. The deletion is acceptable and deletes exactly one tuple.

    Delete example 2

    DELETEthe EMPLOYEE tuple with Ssn = '999887777'from EMPLOYEE
    EMPLOYEE
    FnameLnamePRIMARY KEYSsnSuper_ssnDno
    JohnSmith1234567893334455555
    AliciaZelaya9998877779876543214
    JenniferWallace9876543218886655554
    WORKS_ON
    FOREIGN KEYEssnPnoHours
    9998877773030.0
    9998877771010.0
    9879879871035.0
    987987987305.0
    ✗ REJECTED · REFERENTIAL INTEGRITY

    “This deletion is not acceptable, because there are tuples (rows) in WORKS_ON that refer to this tuple. Hence, if the tuple in EMPLOYEE is deleted, referential integrity violations will result.”

    Why: There are tuples in WORKS_ON that refer to this employee. If the EMPLOYEE tuple were deleted, those references would point to a tuple that no longer exists.

    Delete example 3

    DELETEthe EMPLOYEE tuple with Ssn = '333445555'from EMPLOYEE
    EMPLOYEE

    “This deletion will result in even worse referential integrity violations, because the tuple (row) involved is referenced by tuples from the EMPLOYEE, DEPARTMENT, WORKS_ON, and DEPENDENT relations (tables).”

    Why: Even worse violations: Franklin Wong is referenced by tuples in EMPLOYEE, DEPARTMENT, WORKS_ON and DEPENDENT.

    04

    The Update operation

    Changing attribute values

    The Update operation

    From the lecture · Lecture 4 · Part 3
    • The Update (or Modify) operation is used to change the values of one or more attributes (columns) in a tuple (or tuples (rows)) of some relation (table) R.
    • It is necessary to specify a condition on the attributes of the relation to select the tuple (or tuples) to be modified.
    In plain words

    What an update can violate depends on which attribute changes. An ordinary attribute (e.g. Salary): only its domain (allowed values). A foreign key (e.g. Dno): it must still point to an existing tuple. A primary key (e.g. Ssn): it must stay unique and not NULL, and no tuple may still refer to the old value.

    Changing a primary key works like deleting the old tuple and inserting a new one, so both sets of checks apply (textbook, Section 5.3).

    Update example 1

    UPDATEthe Salary of the EMPLOYEE tuple with Ssn = '999887777' to 28000EMPLOYEE
    EMPLOYEE
    FnameLnamePRIMARY KEYSsnSalaryDno
    JohnSmith123456789300005
    AliciaZelaya99988777725000 → 280004
    JenniferWallace987654321430004
    ✓ ACCEPTED

    “Acceptable.”

    Why: Salary is neither a key nor a foreign key, and 28000 is in its domain (allowed values). The update is acceptable.

    UPDATEthe Dno of the EMPLOYEE tuple with Ssn = '999887777' to 1EMPLOYEE
    EMPLOYEE

    “Acceptable.”

    Why: Dno is a foreign key and Dnumber 1 (Headquarters) exists in DEPARTMENT. The update is acceptable.

    Update example 3

    UPDATEthe Dno of the EMPLOYEE tuple with Ssn = '999887777' to 7EMPLOYEE
    EMPLOYEE
    FnameLnamePRIMARY KEYSsnSuper_ssnFOREIGN KEYDno
    JohnSmith1234567893334455555

    Headquarters1888665555

    “Unacceptable, because it violates referential integrity.”

    Why: No DEPARTMENT tuple (row) has Dnumber = 7, so the new foreign key value refers to nothing. Unacceptable.

    Update example 4

    UPDATEthe Ssn of the EMPLOYEE tuple with Ssn = '999887777' to '987654321'EMPLOYEE
    EMPLOYEE
    FnameLnamePRIMARY KEYSsnSuper_ssnDno
    JohnSmith1234567893334455555
    AliciaZelaya999887777 → 9876543219876543214
    JenniferWallace9876543218886655554

    WORKS_ON.Essn2 tuples (projects 30 and 10)
    ✗ REJECTED · KEY + REFERENTIAL INTEGRITY

    “Unacceptable, because it violates primary key constraint by repeating a value that already exists as a primary key in another tuple (row); it violates referential integrity constraints because there are other relations (tables) that refer to the existing value of Ssn.”

    Why: 987654321 already exists as Jennifer Wallace’s primary key, so the key constraint is violated. The WORKS_ON tuples that refer to the old value 999887777 would also be left pointing at nothing.

    05

    Handling a violation

    What the DBMS can do

    Ways to enforce the constraints

    When an operation would violate a constraint, the DBMS (or the user) can respond in several ways (Elmasri & Navathe, Section 5.3):

    Reject (restrict)

    Refuse the operation and explain why. This is the default.

    Cascade

    Also delete or update the tuples (rows) that reference the one being deleted or changed.

    Set NULL / default

    Set the referencing foreign keys to NULL or a default value (not allowed if the FK is part of a primary key).

    Correct it

    Ask the user to fix the operation, e.g. insert the missing DEPARTMENT 7 first.

    Key takeaways

    1. 01

      Three basic operations change a database state: Insert, Delete and Update (Modify).

    2. 02

      Insert can violate all four constraints: domain (allowed values), key, entity integrity and referential integrity.

    3. 03

      Delete can violate only referential integrity, when other tuples (rows) reference the deleted tuple.

    4. 04

      Update can violate any constraint, depending on whether an ordinary attribute (column), a foreign key or a primary key is changed.

    5. 05

      A violation can be handled by rejecting, cascading, setting NULL or a default, or correcting the data.
